Key Findings

Railway executes npm run start inside wizard/, which shell-substitutes ${PORT:-8080} to the fallback because Railway doesn’t inject PORT for build scripts; the server binds to 8080 so the health check fails and the container is terminated.
http-server (and serve) live in devDependencies, so Railway’s default npm install --omit=dev removes them; npm then tries to download http-server@14.1.1 each boot (npm WARN exec ... in your log) which is fragile and slows cold starts.
The service starts from the repo root; without telling Railway to use wizard/, the platform builds nothing and just serves the checked-in dist/, so any future build-only change would never reach production.
Recommended Fix

Move the static server you rely on into runtime deps and guarantee the correct port: in wizard/package.json set "start": "serve dist --single --listen tcp://0.0.0.0:${PORT:-8080}", move serve (or http-server if you prefer) into "dependencies", and drop the other unused static-server package to avoid ambiguity.
If you want a shell script, rewrite wizard/start.sh to #!/usr/bin/env node\nconst { createServer } = require('serve-static') ... is overkill—stick with the package script above and delete start.sh/Procfile so there’s a single source of truth.
Add a tiny guard so local Windows runs keep working: if you must stay shell-based, use cross-env-shell (already in many setups) or swap to a Node script that reads process.env.PORT || 8080.

Railway assigns each running container a random high port (they pass it in the PORT environment variable) and their router forwards external traffic to that port. Your npm run start command listens on whatever process.env.PORT resolves to. If you set PORT=3000 in the app‑level variables, the container obeys that value, binding to 3000 instead of the one Railway gave it. The router still tries to reach the random assigned port (say 45678), finds nothing listening, and marks the deploy unhealthy.

Delete the custom PORT variable and let Railway inject its own. Your script falls back to 8080 only when PORT isn’t defined (local runs), so production will bind correctly to the assigned port and the health check will pass.

what is npm ci


npm ci (“clean install”) installs dependencies exactly as locked in package-lock.json. It deletes any existing node_modules, skips writing the lockfile, and only succeeds if the lock matches package.json. It’s faster and more deterministic than npm install, so CI/CD pipelines use it to guarantee reproducible builds.

Setting "noEmit": true is a good idea if you only use tsc for type-checking and rely on Vite to produce the actual build output—which is exactly what tsc && vite build does. With "noEmit": false, tsc tries to drop .js and .d.ts files into dist before Vite runs, creating noise and sometimes conflicts (especially because Vite wipes dist during its own build).

If you flip "noEmit" to true, drop the emitter-specific options that no longer make sense:

Remove "outDir": "./dist" and "declarationMap": true, "declaration": true, "sourceMap": true.
Leave "rootDir": "./src" if you still want the compiler to treat src as the source root for path resolution; it can stay even with noEmit.
After that change, tsc will just type-check and exit quickly, while Vite continues to emit the actual bundle.

The 502 Bad Gateway error on Railway.app when deploying a Node + Python web app usually means Railway's Edge Proxy cannot communicate with your application. The most common causes are:

The application is not listening on the correct host and port. Railway requires the app to listen on host 0.0.0.0 and on the port specified by the PORT environment variable that Railway injects at runtime. For example, in Node/Express, you do:

js
const port = process.env.PORT || 3000;
app.listen(port, "0.0.0.0", () => {
console.log(Server running on port ${port});
});
For Python (e.g., using Uvicorn), you must also ensure the server listens on 0.0.0.0 and the injected port:

bash
uvicorn main:app --host 0.0.0.0 --port $PORT
If the app isn't listening correctly on the host/port Railway expects, no errors may appear in logs or build, but the proxy will fail and return 502.

Also, if the configured target port in Railway is incorrect, it can cause this issue.

The application should not just default to localhost or 127.0.0.1, as Railway expects 0.0.0.0 to accept incoming traffic from outside the container.

Steps to fix:

Confirm your Node server and Python server both listen on 0.0.0.0 and on the port from process.env.PORT (Node) or $PORT (Python).

Double-check Railway environment variables are set and that after setting them you redeploy the app (sometimes missing a re-deploy leaves old config active).

Check logs to ensure the servers started and are listening on the expected port.

If you are using a reverse proxy or Docker compose, ensure the ports forwarded are aligned with Railway's PORT variable.

Consider adding explicit logging at server startup to confirm port and host binding.
